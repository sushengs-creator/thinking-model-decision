# 把工具组合成解决问题的工具箱

先建立问题地图，再按实际缺口配置工具；复杂问题可以分阶段使用多个工具，没有“1主＋3辅”的硬上限。一个工具足够就停止增加。“全面”是与此问题有关的重要视角得到处理，而非每次填满七格。

## 检查覆盖，而非套固定套餐

| 需要看清的部分 | 可能改变什么 | 候选入口，阅读正文后再决定 |
|---|---|---|
| 目标和价值 | 什么问题值得先解、什么算好结果 | WW-9.7、WW-9.2、TM-064 |
| 事实和原因 | 哪些解释成立、什么证据尚缺 | TM-001、TM-002、TM-050、TM-054、WW-3.3 |
| 约束和资源 | 什么不可承受、哪里不能假设无限投入 | TM-058、TM-062、TM-077、TM-080、WW-1.4 |
| 参与者和系统 | 谁能决定什么、激励和反馈如何维持局面 | TM-083、TM-097、TM-100、TM-111、TM-114、TM-142、WW-6.14 |
| 时间和后续反应 | 眼前动作会怎样改变下一轮条件 | TM-082、TM-084、TM-092、WW-6.11、WW-8.4 |
| 路径和取舍 | 除既定选项外还有什么可行路线 | TM-063、TM-065、TM-076、TM-105、TM-125、WW-5.5 |
| 执行和反馈 | 怎样开始、如何观察、何时调整 | TM-068、TM-118、TM-121、TM-123、TM-132、TM-141、WW-7.6 |

上述是候选 ID，不是无需阅读的权威配方。根据 [TM 目录](tool-catalog.md)、[WW 目录](wan-catalog.md) 和 [问题路由](decision-routing.md) 搜索其他更适合的机制。对普通简单问题，不因表中有七行就使用七个工具。

## 每个工具要有工位与交接

选择后为每个工具记录：**子问题 → 输入 → 工具特有的转换 → 最小成果 → 交给哪一步或改变什么行动**。在对话中先简短告诉用户分析顺序，例如“先分清原因，再看双方能改变什么，最后比较处理路径和代价”。详尽矩阵放在报告展开区。

已有事实可以并行检验竞争解释、资源和职责；依赖关系应顺序运行。例如原因仍不明时，干预建议保留条件；恢复安排不可行时，不能继续把方案称为可逆；关键人的配合尚未确认时，实施步骤写成待协商。

删除某工具后，如果问题表示、证据、方案和步骤完全不变，就撤下或合并。两个来源讲同一机制不构成两份独立证据。不同角色各自交付一篇泛泛分析，不算组成工具箱。

## 分歧要解决到方案层面

工具出现不同建议，检查：是否服务同一目标，使用同一时间尺度，假设相同系统状态，依据是否独立，是否一个谈收益、另一个指出硬约束。保留尚不能裁定的条件分支，不用投票、平均分或“综合谨慎考虑”掩盖矛盾。

例如可逆性工具认为能够试行，但信息价值工具发现结果三个月后才出现、而承诺一周后就锁定。真正的修正是缩短反馈周期、推迟承诺或停止试验；不能原样保留试验，再加一句“注意风险”。这是虚构机制示例，实际使用需读取两工具并核对现实条件。

## 汇总为一个可以实施的解决方案

用一条主线连接产物：问题怎样形成 → 哪些条件可改变 → 当前方案为什么优先 → 需要什么配合与准备 → 先做什么、后做什么 → 怎样观察结果和调整。

需要取舍时比较有竞争力的替代方案与现实基准；纯解释、学习或协调任务不强造二选一。复杂问题主动寻找反证；缺证据时给工作假说与验证步骤，不强行宣布根因。

把所有工具提出的行动合并成同一预算与日程，计入沟通、准备、执行、查信、等待依赖、复盘及已花成本。一次会面不能被三个工具各算成不同的免费资源；用户只有90分钟就必须整体控制在90分钟内，或者明确提出需要增加资源而未获确认。

区分建议、已同意、已执行和已见效果。对方如何回应只能观察或待协商，不能写成承诺。新工具只在能解决重要缺口时加入；覆盖已足够、再分析不改变动作时结束，交付 [报告与实施步骤](decision-report.md)。
