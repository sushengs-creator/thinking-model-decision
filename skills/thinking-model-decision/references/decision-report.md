# 决策报告交付规范

信息足以支持当前判断或用户要求先出一版时，默认交付自包含的 HTML「下一步行动计划」，包含决策分析与执行安排，用户不必回翻逐轮问答。按 [HTML 交付规则](html-action-plan.md) 保存并验证文件，在对话中给出简短结论和链接，不再询问是否需要 HTML。用户明确指定其他格式或不生成文件时优先遵从；真实个人报告不写进可复用技能包。

## 报告需要回答的问题

先给当前建议，再展开必要证据。下面是报告的内容要求，可按复杂度合并为简短段落或表格，不要求逐字套用标题。

1. **当前建议与前提**：眼下选什么、先做什么、为何。信息不足时标明“阶段性”或“有条件建议”，说明哪个未知会阻止最终判断。避免无依据的百分比或精确评分。
2. **问题定义**：用一句话重述需要决定的事，交代用户的目标排序、硬约束、期限与范围。若开始时的问题在对话中得到修正，说明最终解决的是哪个问题。
3. **事实、假设和未知**：列出真正影响选择的材料，注明来自用户陈述、提供文件或外部核实；用户说过不等于已独立证实。关键未知解释会影响哪项判断，不罗列无关的资料需求。
4. **模型分析与方案比较**：通常一个主模型，至多三个补充或反证工具。引用实际读取的 ID、名称与相关来源，说明该模型如何改变问题表述、比较标准或动作。比较合理备选及有意义的基准，给出收益、代价、依赖与不可恢复后果；适合比较时用表格，不编造数字。检验一个有竞争力的替代解释或方案，不把推断直接写成根因。
5. **行动计划**：先突出眼下第一步，再按实际顺序或条件安排后续。每项关键行动写清做什么、为什么做（对应的事实、约束或已分析的模型）、谁来做、何时或什么触发下做、需要哪些前置条件、产出或完成标准，以及何时调整或停止。简单行动可合并字段为短句；仅在有关联的模型确实改变行动时引用模型，不给每行硬贴模型名。只使用已知或标为建议的责任人、时间、成本和资源；未约定的日期注明“建议”，不虚构他人承诺或代用户对外执行。
6. **风险与修正条件**：最值得注意的失败路径、何时继续/调整/暂停/退出，以及出现什么新证据会推翻建议。区分可以撤回的试验和一次性决定，不能把所有选择都包装成可逆试错。
7. **待确认事项与复盘**：如仍有关键缺口，给出最少必要核实任务；有合适时点或信号时提出复盘建议。不要在报告末尾再发一套大问卷，也不要未经请求设置提醒或监控。

若用户没有提供日期，不捏造决定日或最后期限；需要报告日期时使用实际生成日期。区分用户时限与建议节奏，不机械套用“24小时、7天、30天”。在文件中标明报告日期、初版/修订版/阶段性及适用范围，不把软件版本号当报告日期。

## 交付前检查

按上面七项复核草稿，尤其核对建议及行动是否违反用户的硬约束、关键假设是否被写成事实、引用是否来自实际读过的资料。发现不一致先修正；关键证据不足则交付有条件或阶段性报告，不因催促或指定结论而隐去会改变行动的未知。这个检查由助手完成，不增加用户审批；无需另附打分表。保存后完成 HTML 交付规则中的文件与显示检查；确认文件存在、内容完整，再提供真实路径。对话摘要不能代替应交付的文件。

## 简版与阶段性报告

小决定可以精简为：建议与前提、问题及关键事实、备选比较和模型作用、下一步与更新条件。规模缩小，信息层次仍应清楚。

阶段性报告应把“现在就能做的”“取决于待核实条件的”分开；有必要时明确暂不能可靠地做出最终选择，同时交付信息核实或降低损失的行动。不能因一项信息缺失而把全部内容留空，也不能为了完成报告假装已有定论。

## 后续信息怎样接入

新证据、目标或约束到来后，更新问题定义、受影响的方案比较和行动，简述“什么信息变了 → 哪个判断随之变化”。默认交付更新后的 HTML，保持仍成立的事实与来源，在文件中记录变更原因及旧建议是否适用。更新前保留可回溯的旧版；用户指定覆盖同一文件时也先留备份。看不到原报告时说明缺口，索取报告或摘要，不假装已读历史。决策由用户作出，报告支持其判断，不替其规定人生目标。
