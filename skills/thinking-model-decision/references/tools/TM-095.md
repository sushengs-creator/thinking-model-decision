# TM-095 · 系统韧性

状态：v2运行文件；来源与试跑范围以tool-index.json为准。

## 触发与输入
准备取消冗余、担心主力缺席或单一路径中断时调用。过去没出事、一次抢救成功都不能证明韧性；恢复功能也不等于从冲击获益。最小输入是关键功能、冲击种类、依赖、资源和恢复要求；先问：“这类中断发生时，哪些功能必须保住，最多能停到什么时候？”

## 转换动作
1. 画出受冲击后功能下降、降级运行和恢复的时间线。由真实使用需求确定最低功能、最大中断和可接受代价，不凭空设恢复数字；指出不同人承担什么损失。
2. 沿关键功能检查共同失效：备用路径是否仍靠同一账号、电源、人员或上游。核实备份的容量、权限、知识和启动条件，名单上有备用不等于届时能切换。
3. 对无法绕开的瓶颈安排恢复顺序与临时替代，区分恢复原状和重组后维持功能。旧状态已不适用时不强求还原；将准备、沟通、交接和复查时间计入资源，而非只算切换动作。
4. 可用桌面推演或测试环境验证关键交接；真实演练需有授权、有限范围和停止条件。检查反复超负荷、透支他人或转移损失的办法是否可持续，不把熬夜英雄当长期恢复机制。

## 最小成果与停止
交付“关键功能恢复安排”：最低服务、关键依赖、切换或恢复路径、责任人、时限依据、已核实与未演练项。能够在明确冲击范围内启动即可完成，不宣称应对任何意外。发现共同依赖未解、备用不可启动或代价越界时改方案；冲击、人员、资源或需求变化后重判。

## 工具箱接口
不可承受损失交给安全边际和风险约束；恢复最慢的限制交给瓶颈工具；若要声称扰动让系统更好，再交给反脆弱性并补无冲击参照。建议、负责人接受、准备完成、演练结果和真实恢复能力分别记录，恢复一次只支持相应范围的结论。
