# TM-061 · 事前验尸

状态：v2运行文件；来源与试跑范围以tool-index.json为准。

## 触发与输入
方案已有目标和路径、仍能修改，大家却迅速一致或不敢提异议时用。方案空白不能凭空验尸，已发生失败则应做复盘。需要方案、资源、验收日、失败状态及掌握不同现场信息的人；条件缺失时问：“你们现在已经决定了哪些做法，还有哪些地方来得及改？”

## 转换动作
1. 设定站在未来哪一天回看，以及具体怎样算失败。声明“已经失败”只是生成原因的思考前提，不是概率预测；失败不只指执行差，也可指目标不成立、需求判断错。
2. 各人先独立写原因，再逐轮每人贡献一个未出现的原因；主持人只澄清，不反驳或诱导。权威可后发言以减少锚定。个人使用也先写完再筛。不得替未参与者虚构他们的意见，无法召集时标出缺席视角。
3. 将零散原因连成“起因—放大—未及时纠正—失败”的路径，区分已见事实和推测。依据证据、后果与可逆性筛关键路径，不能靠生动程度或多数票删除单人掌握的重大信息。
4. 对重点路径修改原方案，列需要核实的假设、可做的防范和早期信号。接入执行时明确监测人、触发动作及暂停权限；这些是落地增强，不冒称为原始方法的全部固定步骤。

## 最小成果与停止
交付关键失败路径、待核实事项和一份相对于原计划的具体修改单；仅让大家更悲观不算完成。每条优先路径有改动、待查理由或可接受的剩余风险即可结束。没有成形方案先停用；范围、核心人员或环境显著改变时重做。提出、接受、落实修改和实际降低失败分别记录。

## 工具箱接口
需核实死因时交给证据或实验工具；已有特定冲击要看能否承受时交给压力测试、安全边际；出现缺少需求的根本问题时回到问题澄清。该工具生成风险假设，不能直接证明方案必须停止。
