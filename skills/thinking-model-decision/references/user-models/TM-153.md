三个人都有空，会议为什么还是约不成？

假设你要约一场会，老张、老李、小王必须一起参加。只考虑本周二、周四、周五下午两点到三点，会议室这三个时段都能用。

老张说，周二、周四有空。老李说，周四、周五有空。小王说，周二、周四有空。

每个人都有两个选项，听上去不难安排。把三份时间放到一起，却只有周四能开。

这时老李又说，周四临时有事，只剩周五了。

现在，三个候选时段中没有一个能让所有人到齐。老李有空的周五，另外两人没空；另外两人有空的周二、周四，老李没空。再换一间会议室，也解决不了这个冲突。

每个人报的时间都没错，合起来却约不出一个共同时间。

你协调好了每件事，为什么最后还是拖延了？

再设想一个项目，涉及设计、开发和测试三个组。开发说需要三周，设计说要先出两版方案，测试说要留两周回归测试，也就是检查修改有没有影响原来正常的功能。

你开始协调。开发能不能少用几天，设计能不能少做一版，测试能不能压缩到一周。最后，时间表上的每一行都短了一点，大家也点了头。

可项目跑起来，开发在等设计定稿，测试在等接口交付。

继续压缩某一组的时间，未必能让整个项目提前。真正的问题在别处，各组报了自己的工期，却还没把相互依赖写进同一张表。

每个人都没错，为什么就是凑不到一起

上面两件事看着不一样，却卡在同一个地方。

约会那件事，卡在三个人没有共同的空闲时段；项目那件事，卡在各组工期还没有与前后依赖衔接起来。单独看各自的条件，还不能判断整套安排是否可行。

你以为在挑方案。挡住你的是条件：这些条件能不能同时成立。

有个思维模型专门管这件事，叫约束满足。这个名字来自人工智能研究，早期一条重要的推动路径是计算机视觉：计算机要在多个可能的解释中，找出能同时满足各项条件的组合。蒙塔纳里（Ugo Montanari）、沃尔兹（David Waltz）、麦克沃思（Alan Mackworth）等研究者都作出过重要贡献。后来的排课、排班、排产，也照这个路子处理。把这套框架用到日常安排上，第一步也是把要决定的事、可选范围和共同限制说清楚。

它把这类问题当成一道题来处理，一道题由三样东西组成。

变量，是要决定的事。开头的例子里，是这场会安排在哪个时段。项目排期中，是各项任务什么时候开始、由谁负责。

取值域，是每件事允许选择的范围。那场会的候选时段是周二、周四、周五。任务的候选负责人，可以是具备相应能力、能够参与的几个人。

约束，是安排必须遵守的条件。会议时段必须落在每个人有空的时段里。依赖设计定稿的开发任务，不能在定稿前开始。同一个人不能在同一时间承担两项无法兼顾的工作。

约束满足这个思维模型，问的就是能不能找到一套完整安排，让所有条件同时成立。这样的安排叫可行解。

这三样摆在一起，就是这道题的全部内容。开头那场会，摆着的是三个人的空闲时间、一间会议室；哪个时段能让三个人同时到，就是答案。

这里有一条规律值得先记住：在要决定的事和可选范围不变时，新增一条必须满足的条件，可行安排不会因此增加。它可能不排除任何方案，也可能一下排除很多。关键不只是条件有多少，还在于它们怎样相互限制。

三个人各有两个空档，并不等于会议有六个时段可选。会议只能选三人共同有空的时段。人再多几个、条件再细几层，可选的余地只会更紧，不会更松。这也是排期、排班这类事越到后来越难的原因。

这个定义里最容易被忽略的一点，是它不问哪套安排更好，只问有没有一套安排能同时成立。

先问有没有符合要求的安排，再问哪套更值得选，能减少很多无效比较。很多人卡在这样的处境里出不来，是因为一直在比较一个还不存在的选项。

我们把这个定义拆开来看。

它检查的是「同时成立」。十个条件，逐个检查每一个，十个都过得去。这并不说明十个能放在一起。开头那场会就是最清楚的例子，三个人的时间表分开看都没问题，合起来只剩一个选择，再多一个变化就彻底没有。做项目时也一样，每个部门报上来的计划单独看都合理，可它们共用同一批人、同一段时间，合起来就可能打架。

它交付的是一套完整安排。你缩短了开发的工期，砍掉了设计的版本，每一处都在优化，可这套安排还没被完整检查过。约束满足要求你把所有事都确定下来，确定成一套，然后逐条核对它合不合格。安排到一半也可以检查，并在发现冲突时及时退回；但只有一套完整安排通过全部硬条件的检查，才能说找到了可行解。

它承认有些局面真的没有解。这一点后面会展开讲，但先记住：老李把周四改成周五之后，这件事就没有解了。此时你要做的是回头动条件。模型不只告诉你「有解」，也会告诉你「在现在这些条件下，没有解」。

硬条件，和可以商量的偏好

这里还要分清硬约束和软约束。

「必须全员参加」如果是本次会议不能让步的要求，就按硬约束处理；「最好别安排在下班前」如果允许权衡，就是一项偏好。

举一个小例子。假设约四个人吃饭，其中一位下班后要赶回家接孩子，八点前必须走。这一条在这个场合是硬的，不是偏好，改不了。另一条是「最好找离公司近的地方」。这条可以商量，只要说清楚理由，去远一点也能接受。这就是硬和软的区别：硬的动了就吃不成这顿饭，软的动了只是这顿饭麻烦一点。

偏好不是无关紧要的习惯。它可能有充分理由，只是允许商量，不等于可以随手抹掉。

找一套能同时成立的安排时，只拿硬条件来算。想把成本、便利、风险也算进去比较，那是另一道题，得先确定评价标准。

检查也不必等到全部安排完才做。安排到一半就发现冲突，可以立刻退回。不过局部检查通过，还不能宣布整套方案可行。

「还没找到」和「确实没有」，不能混为一谈

处理这类问题，要分清三个状态。

找到了一套可行方案。所有需要决定的事都已确定，这套安排满足已列出的全部硬条件。

证明当前条件下没有解。有足够的依据排除所有可能。老李只剩周五，另外两人周五都没空，在限定的三个时段内就不存在共同时间。

尚未判定。试过一些方案，还没找到，也没有足够依据说不存在。可能需要换个寻找顺序、补充信息，也可能因为时间或成本限制，暂时停止。

「我试了三种安排方式，都不行」通常只说明这三种安排方式失败。它与「任何安排方式都不行」之间，还差一段证明。

数独有一个现成的例子，能把这件事说透。

标准 9×9 数独中，有唯一答案的题目最少需要几个已知数字？此前已经有人找到 17 个线索的题目，却一直没找到只有 16 个线索而答案唯一的题目。研究者因此猜想，下限是 17。

2012 年，爱尔兰都柏林大学学院的加里·麦圭尔（Gary McGuire）和两位合作者公开了一项计算机辅助证明。他们通过数学化简和穷尽搜索，排除了存在 16 线索唯一解题目的可能。论文报告，计算共用了约 710 万核小时，也就是把各个处理器核心的工作时间相加；任务在 2011 年内完成。

这里排除的是「有唯一解」。一个只有 16 个线索的盘面，如果至少有一个解，就一定还有别的解；如果给出的数字彼此矛盾，也可能根本无解。17 是最小可能值，不表示任意给出 17 个数字就能保证答案唯一。

这个例子说明：没有找到，和有依据排除全部可能，是两种不同的结论。

日常安排不必每次都检查到这种规模，但结论要跟依据相匹配。暂时停止寻找时，可以明确说：目前还没找到，我们检查到了这里。

安排不下去的时候，先分清是选错了还是条件太紧

如果你被某件事情卡住了，先分清是安排方式的问题还是条件的问题。

一种是你选错了顺序、选错了位置，换一种安排方式还能安排开。另一种是这几条要求本身就不可能同时满足，换多少种安排方式都没用。

分不清这两种，就会一直做无用功：明明该回头改条件，却一遍遍重新安排；或者明明只是这一种安排方式不合适，却急着去改别人的要求。

冲突提供了一条需要追查的线索，但还不能直接告诉你哪条条件必须改变。

老李改成只有周五那天，这道题就安排不下去了。这一次安排不下去，可能只说明这一次选择走不通，也可能暴露了几条要求无法兼容。

先分清这两种情况，才能决定是换一种安排，还是回头讨论条件。

多数人把冲突当成坏消息，一遇到就想着绕过去、糊弄过去、或者多使点劲。所以反复改方案，磨到一个大家都勉强点头的版本，然后带着一个隐藏的冲突上路。把冲突当线索的人，看到冲突的第一反应是问一句：它是只否掉了这一次选择，还是这几条要求本身碰上了。

如果只是某个选择让后面安排不下去，就撤回这个选择，试试其他安排方式。若还没检查完全部可能，不能因为累了，就认定现有条件必须改变。

如果已经确认这些要求无法同时满足，就该回头检查：条件是不是记录错了，有没有过时的信息。如果条件确实如此，再讨论任务能否调整。发现信息有误，无论检查到哪一步，都应及时纠正。

即使还没判定，有权决定的人也可以因为寻找成本太高，主动扩大日期范围或调整任务。但这等于换了一道题，不能反过来声称原来那道题已经证明无解。

老李只能周五，另外两人周五都不行。如果仍要求三人共同参加，就需要有人调整时间，或者把日期范围扩展到下周。若参会目的允许，也可以讨论是否改变参会方式。每种改变都要重新核对能否满足会议目的。

调整哪一条，要由有权决定的人权衡代价。模型能帮助找出互不相容的要求，却不会替你决定谁应该让步。

这里要把「硬」这个字说准：「硬」表示在当前这件事里必须满足，不表示所有要求永远不能调整，也不表示只要安排不出来就有权修改。真实的要求可能彼此不相容。获准调整时，可以延期或缩小任务；不能调整时，就只能暂缓或停止当前任务。

项目里也一样。三周工期依据什么估计？两版设计是不是必要的比较？两周测试对应什么工作量和风险？先把理由问清楚，再谈能否调整，不能把所有余量都当成可以削掉的习惯。

有些条件确实动不了，动了就是违规、出事故、得罪人，这些接受就是了。但多数人卡住的地方不在这儿。他们卡在把习惯当成了硬条件，从来没伸手去问一句这条是谁确定的。

一条路走不通，退回去时要把删掉的选择还回来

换一个能一笔一笔算清的例子：三场课共用一个教室，每场占一个完整时段，三场不能重叠。

A 课能选时段 1 或 2，B 课能选 2 或 3，C 课能选 1 或 2。

先试着把 B 放在时段 2。B 占了 2，A 和 C 就都不能选 2，各自只剩 1。接着把 A 放在 1，C 就没位置了。

这条路走不通，得退回去。

退回去不能只撤最后一步。B 还占着 2，A 和 C 的选项就回不来。要把 B 一起撤掉。B 一撤，A 和 C 重新有 1 和 2 两个选择，B 自己也可以改试 3。

漏掉这一步的后果很隐蔽。A 和 C 的时段 2 从此永久消失，后面无论怎么试都碰不到这条路。明明有解，你会以为自己已经查遍了。

还回来之后接着试。B 在 3、A 在 1、C 在 2，三场都排妥。把 A 和 C 的时段对调，也成立。

这个动作叫回溯，就是往回走。它真正难的地方，是走的时候要把带走的选项一并放回去。

这个例子共有 2×2×2，也就是八种候选组合，其中只有两种可行。八种不多，你自己拿笔列一遍也只要一分钟，就是上面那两种对调。

两种都要求 B 在 3。B 必须在 3，是几条条件放在一起推出来的，单看 B 的选项看不见。

如果再把条件改成「B 只能选时段 2」，这道题就没有解。A 和 C 都只剩 1，却不能共用。这里能证明的是整个题无解；前面的失败，只证明 B 选时段 2 这条路走不通。

先处理哪一件事，和这一件事选哪个选项，是两个问题

事情多了，尝试的顺序会影响你绕多少路。有两条常用的经验。

第一条，先处理可选项最少的那一件。

道理不难理解。可选项越少，越容易被别人的选择挤掉。别人一动，它可能就没位置了。所以先把它安排定，别留到最后。

在三课例子里，假如已经把 A 安排在 1，C 就只剩 2，B 还有 2 和 3。这时可以先确定 C，再让 B 安排在 3。

第二条，为某件事选位置时，优先尝试对别人限制较少的那个。

回到最初的三课条件，假如准备给 B 选时段。B 选 2，会让 A 和 C 各失去一个选项；B 选 3，不会占用它们的候选时段。因此，先试 3 更有理由。

一条回答先处理哪一件，一条回答给它选哪个选项。它们都是经验，不敢保证最快，也不敢保证一定有解。

放到工作里，可以先看哪件事的可选安排最少，优先处理它；给它选具体时间或位置时，再比较哪个选择能给其他事项留下更多余地。做完这一步，仍要继续检查整套安排。

哈勃的观测计划，也要一处处修冲突

三场课可以拿笔列完，哈勃望远镜的观测安排就复杂得多。不同观测有各自可用的时间，有些还要求特定的先后顺序或间隔。

据当时的报告，哈勃每年需要安排约一万到三万次观测。空间望远镜科学研究所从 1987 年开始开发 SPIKE，1990 年 4 月哈勃发射后不久投入使用。它管的是较长时间范围内的安排，具体执行的短期指令另有环节负责。

SPIKE 最早用神经网络来做修复。这套办法后来被提炼成一套简单的符号化规则，也就是「最小冲突」，神经网络随之被替掉。这套思路先形成一套完整、但可能还有冲突的初始安排；再挑一个正在冲突的任务，尝试把它放到当前冲突最少的位置，反复修正。

初始安排做得好不好，会影响后面要修复多少冲突，这一步仍要认真做。这种局部修补也不保证每次都能找到解，达到时间或尝试次数上限后还没成功，不能据此说无解。

多往后检查一步，能不能少推翻几次

找方案时，可以给一件事确定下来后，只检查它与已确定事项有没有冲突；也可以再看看，这个决定让后面的人还剩哪些选择。

后一种做法中，一个常见方法是每确定一个值，就检查与它有约束关系、但还没确定的事项，把已经不可能的选项排除掉。如果谁的选项被删空，就立刻退回。

仍用三课例子。先确定 A 安排在 1，B 剩 2 或 3，C 只剩 2。如果接着试 B 安排在 2，这一步检查就会删掉 C 最后的选项，不用等到正式给 C 安排时间，便知道这条路失败了。

不过，各项都还剩选项，也不代表后面一定安排得下。假如一开始就确定 B 安排在 2，A 和 C 各自都还有 1，单看都没有被清空；可两场课都要用同一间教室的同一时段，合起来仍有冲突。发现这种冲突，需要进一步检查，或者接着往下推。

检查得更细，会增加当下的工作，却可能减少后面的返工。这时候可以问一句：如果走到最后才发现冲突，回头要付出多大代价。代价越大，越值得提前检查清楚关键依赖。

两两都能配合，为什么三个一起还是不行

假设一个系统上线前，产品、开发、运营分别说，我这边没问题。

但产品确认的是新版需求，开发依据的是旧版接口，运营安排的推广日又碰上维护时间。每个人检查的对象不一致，三句承诺还不能说明整套方案可行。

更容易漏掉的是，即使任意两方都能找到配合办法，所有人也未必有一套共同办法。

把三课例子再改一下。A、B、C 都只能选时段 1 或 2，仍然只有一个教室。任选两场课，一场安排在 1、一场安排在 2，都能办。三场一起安排，就必然有两场落在同一时段。

两两对得上，加起来未必对得上，这就是局部和整体的差别：每一对都合格，不代表同一份安排里所有人都能过关。

任意两场课都能安排开，是因为每次只解决了两场课的问题。最终要验证的，是同一份包含全部事项的安排。

所以，「我们两边对过了」还要接着问一句：对的是不是同一版日期、同一份需求、同一组资源。

条件变了，旧方案还能直接用吗

条件写清后，还要有人维护。

家里的周末安排就是这样。孩子上午有课，老人下午要午休，车只有一辆，下午三点还约了人。上一周排好的样子是：九点开车送孩子，十一点回来顺路买菜，午后老人在家休息，我们把车开出去三点见人。四个人就这么错开了。这时孩子说，周六的课改到了周日早上。先把这个变化写进表里，再检查接送、用车和周日的其他安排是否冲突。也许只要调整接送，也许还要连带改动别的事；不能沿用旧结论，也不必预先认定整张表都要重排。

工作里也一样。本周能参加的人，下周可能出差；已经确认的接口，可能调整交付日期；季度计划中途也可能插入新的任务。旧方案对旧条件成立，不代表对更新后的条件仍然成立。

变化并不必然要求推倒重来。条件变了之后怎么重新求解、能不能利用上一次的结果，这个方向也有人专门研究。

实际工作中，先更新改变的条件，检查旧方案是否仍满足要求。如果不满足，再找受影响的安排，必要时重新寻找。只改动相关几行，也可能需要检查整张表是否仍然协调。

模型不会自动知道现实发生了什么，也不会替你判断一条新要求是否必要。谁负责更新条件、条件由谁确认，都得落实到人。

下一次卡住，可以按这个顺序检查

准备一张纸，把下面这几件事走一遍。

先写清要决定什么、可以选什么。不要只写「尽快开会」，要写明候选日期、时段、时长和必须参加的人。

然后把相关条件放在一起。除了每个人自己的限制，还要写出共同资源、先后依赖。区分必须满足的要求与可以权衡的偏好，记录条件的依据和确认人。

接着先试一套安排并保留尝试记录。先处理选择少的事项，考虑对其他事项的影响；走不通时，撤回对应假设，恢复因此删掉的选择。

试出这一套之后，检查同一套完整安排。局部确认不能代替整体确认，大家核对的应是同一版信息。

最后给出与证据相符的结论。找到解，就说找到了一套；证明无解，说明冲突在哪里，再由相关人决定是否调整任务；还没判定，就说明检查过什么、为何停下，以及下一步准备补充什么。

还有两件事它管不了。一件是哪套方案更值，找到可行安排之后，比较成本、风险和便利，那是另一道题。另一件是系统里哪个环节最窄。另有一个名字很像的理论叫「约束理论」，问的是系统产出被哪个最窄的环节卡住，跟这里不是一件事，别混。

再约那场会，先把哪张表拿出来

回到老张、老李、小王。老李只剩周五，另外两人周五都没空。

把候选时段与三个人的空闲情况写在同一张表里，就能说清结论：在这三个时段内，按当前的全员参会要求，没有共同时间。

接下来要谈的事情也清楚了。谁能调整原有安排，能不能延到下周，或者是否允许改变会议方式。若这些都不允许，就要承认这场会暂时开不成。

最容易做的事，是把三个人再叫一遍，重新问一轮时间，指望着有人肯让一步。这套动作你已经重复过好几遍了，结果你也知道。换个动作，把这几条条件摊在桌上。哪几条是别人确定的，哪几条是你自己以为的，一条条写下来，标注上硬和软。你会发现，很多看着不能动的东西，其实一直没人真正确定过。

说到这里，可以换个心情看待条件这回事。

条件多、处处受限，刚开始做安排的人通常会把它当成坏消息，因为你不能想怎样就怎样。换个角度，它其实是个好消息：你能算，别人也能算；你能被条件卡住，卡住你的那个条件也卡着别人。事情有边界，才有得谈、有得检查、有得比较。要是这世上说什么都能成，那才真没法安排任何事。

回到会议室那三个人身上，道理也是这个。老李的周四、老张的周二，都是实实在在的边界。正因为边界清楚，才有得让、有得换、有得算。

模型档案卡

模型名称

约束满足（约束满足问题，Constraint Satisfaction Problem）

一句话定义

在给定的一组条件和可选项中，检查能不能找到一套完整安排，让所有条件同时成立。

来源

来自人工智能中的约束满足问题研究。蒙塔纳里（Ugo Montanari）1974 年的《Networks of Constraints: Fundamental Properties and Applications to Picture Processing》是早期代表文献之一；相关框架与算法由多位研究者共同发展。

核心机制

把要决定的事拆成变量、取值域和约束，找一套完整安排逐条核对；分清「找到解」「证明无解」「还没判定」；一种安排方式走不通时，先分清是这种安排不行，还是这几条要求本身不能同时成立。

解决什么问题

多项安排共用资源、相互依赖，单独看都合理，凑到一起落不下去。

调用提醒

要决定什么？有哪些可选项和共同限制？我检查的是不是同一套完整安排？现在是找到了、证明没有，还是还没判定？

边界

适用：能把要决定的事、选项和条件说清的安排类问题。不适用：比较哪套更划算，或定位系统里哪个环节最窄（那是企业管理顾问高德拉特提出的约束理论）。

如果身边有人正卡在一件怎么安排都安排不开的事上，可以把这篇文章分享给他。两个人一起把条件摊开，看看是不是有一条其实一直没人动过。你说的「实在没办法了」，是试过几种都不行，还是已经看清哪几条要求没法同时成立？

事情有边界，才有得谈、有得检查、有得比较。
